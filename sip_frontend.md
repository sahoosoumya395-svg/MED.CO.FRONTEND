# 1 Project Overview

## 1.1 Project Name

**Health Bridge** - also referred to internally as `MED.CO.FRONTEND` or `health-bridge-ui` (per `package.json`).

## 1.2 Purpose

Health Bridge is a **web-based Hospital Management System (HMS)** frontend application built using **Angular 22**. It serves as the patient-facing and administrator-facing interface for a comprehensive healthcare platform. The application enables:

- Patients to register, book appointments, view prescriptions, and check billing records.
- Doctors to view their dashboards, manage availability, request leave, and view their schedules.
- Administrators to manage the entire hospital ecosystem including patients, doctors, billing, and appointments.

The application communicates with a **Spring Boot backend** running on `http://localhost:8082` via a **REST API** integration.

## 1.3 Business Domain

**Healthcare IT** - Hospital Management System (HMS) / Electronic Medical Records (EMR) / Revenue Cycle Management (RCM).

The tagline embedded in the UI code reads:

> *"A next Level Evolution In Healthcare IT, Web Based EMR, Revenue Cycle Management Solution. Designed To Meet The Opportunities."*

## 1.4 Problem Statement

Traditional hospitals rely on paper-based records, disconnected billing systems, and fragmented patient data. Health Bridge aims to solve:

1. **Disconnected records** - centralize patient medical history, prescriptions, and billing.
2. **Manual appointment booking** - automate scheduling based on doctor availability.
3. **Inefficient billing** - generate digital invoices with itemized medicine costs, doctor fees, service charges, and tax.
4. **Lack of role-based access** - provide distinct dashboards and permissions for Admin, Doctor, and Patient roles.
5. **Poor visibility** - give administrators real-time analytics on appointments, bed occupancy, and department-wise patient distribution.

## 1.5 Target Users

| Role | Description |
|---|---|
| **Admin** | Hospital administrator who manages doctors, patients, appointments, billing, and system settings |
| **Doctor** | Medical professional who views appointments, manages availability, requests leave, and adds prescriptions |
| **Patient** | End user who registers, books appointments, views prescriptions, and accesses billing history |

## 1.10 Known Limitations

1. **Route Guards not enforced** - All four guards (`authGuard`, `adminGuard`, `doctorGuard`, `patientGuard`) return `true` unconditionally, meaning no route is actually protected at the time of this documentation.
2. **Hardcoded keys** - The AES-256 encryption key (`HealthBridgeSecretKeyForAuth1234`) and IV (`1234567890123456`) are hardcoded in the client-side source file (`encryption.util.ts`), which is a security concern.
3. **No Token Refresh** - The JWT interceptor attaches the token, but there is no refresh token mechanism.
4. **Dummy/Fallback Data** - Several components (Patient Dashboard, Patient Billing Details) fall back to hardcoded dummy data when API calls fail.
5. **Alert usage** - Some components use native browser `alert()` for feedback instead of styled notifications.
6. **No lazy loading** - All routes are eagerly imported in `app.routes.ts`.
7. **No centralized environment-based API URL** - Individual services use hardcoded `http://localhost:8082` directly instead of reading from the `environment.ts` file.
8. **Typo in component name** - `MyShedule` (should be `MySchedule`) present in the doctor module.

## 2.1 Frontend Framework

**Angular 22.0.0** - The latest major version of Angular, using the modern **standalone component architecture** (no `NgModule`). The project was generated using Angular CLI version 22.0.9.

### Why Angular?

Angular is chosen because:
- It provides a complete, opinionated framework (routing, forms, HTTP, DI all built-in).
- Strong TypeScript support aligns with enterprise-grade healthcare software requirements.
- Standalone component API reduces boilerplate compared to traditional NgModule patterns.
- Server-Side Rendering (SSR) support via `@angular/ssr` improves SEO and initial load time.

The main application features, each in its own directory. Each feature directory typically contains:
- `feature-name.ts` - TypeScript component class
- `feature-name.html` - HTML template
- `feature-name.css` - Component styles
- `feature-name.spec.ts` - Unit test file

### `src/environments/` - Environment Configuration
Single `environment.ts` file with `production: false` and `apiBaseUrl: ''`.

### `src/assets/` - Static Assets
Images, logos, and other binary assets served by the application.

```
                              |
+---------------------------------------------------------------+
|            Spring Boot Backend (localhost:8082)                |
+---------------------------------------------------------------+
```

## 4.2 Component Architecture

All components are **standalone** (Angular 22 recommended approach). There are no `NgModule` files. Each component declares its own imports:

```typescript
@Component({
  selector: 'app-example',
  standalone: true,
  imports: [CommonModule, FormsModule, RouterLink],
  templateUrl: './example.html',
  styleUrl: './example.css'
})
export class Example {}
```

Component communication:
- **Router State** - Used by `Billing` to `FinalBill` (navigation state carries invoice data).
- **Input binding (`@Input`)** - `FinalBill` has `@Input() billData`.
- **Dependency Injection** - Services injected via constructor.

## 4.3 Routing Architecture

Single-level flat routing defined in `app.routes.ts`. All routes are directly imported and registered in one array. No lazy loading, no child routes.

```
Routes Array (app.routes.ts)
+-- ''               -> LandingPage (default)
+-- '/login'         -> Login
+-- '/admin-dashboard'  -> AdminDashboard
+-- '/doctor-dashboard' -> DoctorDashboard
+-- '/patient-dashboard' -> PatientDashboard
+-- '/patient/*'     -> Patient management routes
+-- '/doctor/*'      -> Doctor management routes
+-- '/appointment/*' -> Appointment routes
+-- '/prescription/*' -> Prescription routes
+-- '/billing'       -> Billing
+-- '/final-bill'    -> FinalBill
+-- '**'             -> redirectTo ''
```

The router is configured via `provideRouter(routes)` in `app.config.ts`.

## 4.4 Feature-Based Architecture

Each feature lives in its own directory under `src/app/features/`. This promotes separation of concerns. Each feature owns its component, template, styles, and (in the case of `doctor/`) its own models and services.

## 4.5 Shared Module Architecture

`src/app/shared/components/` contains reusable UI components that are intended to be imported across features. All 8 shared components are **scaffolded but empty** (their HTML templates contain placeholder text of about 20-30 bytes, e.g., `<p>confirm-dialog works!</p>`).

## 4.6 Core Module

`src/app/core/` acts as Angular traditional "CoreModule" pattern, adapted for standalone components:
- **Guards** - route protection logic.
- **Interceptors** - cross-cutting HTTP concerns.
- **Services** - globally-provided singleton services (`providedIn: 'root'`).
- **Utils** - pure functions without DI.

## 4.7 Authentication Flow

```
User visits /login
    |
CAPTCHA loaded (from backend or generated client-side)
    |
User enters email, password, captcha
    |
Client-side captcha validation (if no backend image)
    |
Password encrypted with AES-256-CBC (encryptPassword utility)
    |
POST /api/auth/login
    |
Response checked for statusCode === 200
    |
JWT token saved to localStorage ('auth_token')
User name saved to localStorage ('user_name')
    |
Role-based navigation:
  ADMIN  -> /admin-dashboard
  DOCTOR -> /doctor-dashboard
  PATIENT -> /patient-dashboard
```

## 4.8 Data Flow

```
Component -> Service Method -> HttpClient -> Backend API
                                              |
Component <- subscribe(next/error) <- Observable
```

Locally:
```
Login Component
  -> authService.login(credentials)
    -> HttpClient.post('/api/auth/login')
      -> JWT Interceptor skips (auth URL)
        -> Backend Response
  -> .next(res) -> saveToken() -> navigate by role
  -> .error(err) -> showError() -> refreshCaptcha()
```

## 4.9 API Flow

```
Component calls Service method
    |
Angular HttpClient prepares request
    |
JWT Interceptor intercepts request
    |
If URL contains '/auth/' -> skip token attachment
Otherwise -> clone request + set Authorization header
    |
HTTP request sent to backend (via proxy: localhost:8082)
    |
Response returned as Observable
    |
Component subscribes and handles next/error
```

# 7 Authentication

## 7.1 Authentication Strategy

**JWT (JSON Web Token)** based authentication.

The backend issues a JWT token upon successful `POST /api/auth/login`. The frontend stores this token in `localStorage` and attaches it to all subsequent HTTP requests via the JWT interceptor.

## 7.2 Login Flow

`
1. User enters email, password, captcha answer
2. Client validates captcha locally
3. Client encrypts password with AES-256-CBC
4. POST /api/auth/login with { email, password: encryptedPassword }
5. Backend validates credentials
6. Backend returns { statusCode: 200, data: { token, name, role } }
7. Client stores token via authService.saveToken(token)
8. Client stores name via authService.saveUserName(name)
9. Client navigates based on role:
   - ADMIN  -> /admin-dashboard
   - DOCTOR -> /doctor-dashboard
   - PATIENT -> /patient-dashboard
`

## 7.3 Token Storage

`	ypescript
// AuthService methods

  localStorage.setItem('auth_token', token);
}

getToken(): string | null {
  return localStorage.getItem('auth_token');
}

saveUserName(name: string): void {
  localStorage.setItem('user_name', name);
}

## 7.4 JWT Interceptor

**File:** `src/app/core/authentication/interceptors/jwt-interceptor.ts`

`	ypescript
export const jwtInterceptor: HttpInterceptorFn = (req, next) => {
  if (typeof window === 'undefined') return next(req);

  const authService = inject(AuthService);
  const token = authService.getToken();

  if (token && !req.url.includes('/auth/')) {
    const cloned = req.clone({
      setHeaders: {
        Authorization: Bearer 
      }
    });
    return next(cloned);
  }

  return next(req);
};
`

**Behavior:**
- Skips on SSR (server-side) where `window` is undefined.
- Skips token attachment for URLs containing `/auth/` (login, register, etc.).
- Attaches `Authorization: Bearer <token>` header to all other requests.
- Uses Angular functional interceptor pattern.

## 7.5 Logout

**Current implementation:** The patient dashboard has a `logout()` method that only navigates to `/login`. Token is **not cleared** from localStorage during logout. This is a **known issue**.

## 7.6 Password Encryption

**File:** `src/app/core/utils/encryption.util.ts`

`	ypescript
const KEY_STRING = 'HealthBridgeSecretKeyForAuth1234';
const IV_STRING = '1234567890123456';

export async function encryptPassword(plainText: string): Promise<string> {
  const keyBytes = new TextEncoder().encode(KEY_STRING);
  const ivBytes = new TextEncoder().encode(IV_STRING);

  const cryptoKey = await window.crypto.subtle.importKey(
    'raw', keyBytes, { name: 'AES-CBC', length: 256 }, false, ['encrypt']
  );

  const encoded = new TextEncoder().encode(plainText);
  const encrypted = await window.crypto.subtle.encrypt(
    { name: 'AES-CBC', iv: ivBytes }, cryptoKey, encoded
  );

  return btoa(String.fromCharCode(...new Uint8Array(encrypted)));
}
`

**Security Notes:**
- Key and IV are **hardcoded** in client-side JavaScript (visible to anyone via browser developer tools).
- Uses AES-256-CBC which is an appropriate algorithm but the implementation exposes key material.
- In production, this should be replaced with HTTPS-only transmission and server-side hashing.

Frontend code checks `res.statusCode === 200` to determine success.

  error: (err) => {

# 16 Error Handling

## 16.1 Client-Side Error Handling
1. **Form Validation:** Reactive and template-driven forms provide immediate feedback. Submit buttons are typically disabled (`[disabled]=form.invalid`) until requirements are met.
2. **API Error Catching:** Components subscribe to `HttpClient` observables and implement the `error` callback. 
3. **UI Feedback:** Errors are displayed to the user via simple text elements (e.g., `<div class=text-danger>{{ errorMessage }}</div>`) or native browser `alert()` dialogs.

## 16.2 Global Error Interceptor
**Not Implemented.** There is no global HTTP error interceptor to handle common errors like 401 Unauthorized, 403 Forbidden, or 500 Internal Server Error globally. Components must handle these individually.

## 16.3 Fallback Data
In some dashboard components (Patient Dashboard, Patient Billing Details), if the API request fails, the application gracefully degrades by catching the error using RxJS `catchError` and returning mocked/dummy data using `of()`.

# 17 Security

## 17.1 Authentication & Authorization
- **JWT (JSON Web Tokens):** Used for stateless authentication. Stored in `localStorage`.
- **Role-Based Access Control (RBAC):** UI routing directs users to different dashboards based on their role (ADMIN, DOCTOR, PATIENT).
- **Route Guards:** Scaffolded but currently bypass all checks (return `true` unconditionally).

## 17.2 Data Security
- **Password Encryption:** Passwords are encrypted on the client side using AES-256-CBC before being sent to the server. (Note: Hardcoded keys in client code pose a security risk).
- **HTTPS:** Configurable via environment, but currently defaults to HTTP (localhost proxy).

## 17.3 Vulnerabilities & Risks Identified
1. **Hardcoded Encryption Keys:** `HealthBridgeSecretKeyForAuth1234` and `1234567890123456` are visible in the source code.
2. **Inactive Route Guards:** Protected routes can be accessed by unauthenticated users by directly navigating to the URL.
3. **XSS Protection:** Relies entirely on Angular's built-in DomSanitizer and template escaping. No specific Content Security Policy (CSP) headers are configured.
4. **Token Storage:** JWT is stored in `localStorage`, which is vulnerable to XSS attacks. `HttpOnly` cookies are generally recommended for sensitive tokens.

# 20 Performance

- **Standalone Components:** Reduces module overhead and bundle size.

- **Third-Party Libraries:** ApexCharts is heavy. Ensure it's only loaded when rendering the Admin Dashboard.
